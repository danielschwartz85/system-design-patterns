The 8 system design patterns that keep coming up

The same engineering problems appear again and again across very different products. Learn to recognize the pattern, apply the standard solution, and spend your time on the decisions that make a particular problem interesting.

8 patterns What, why and how Trade-offs Interview scripts

Why patterns?

The more system design problems you look at, the more you notice that the underlying problems repeat:

  • Uber and Yelp: both work with location data and must efficiently find what is near a point.
  • Ticketmaster and Airbnb: when two people try to buy the last seat, or book the same property for the same night, only one may win.
  • YouTube and Dropbox: uploading a 4 GB file raises the same challenges whether it is a video or a document.

Strong candidates recognize these patterns almost immediately. They already know how to handle the common problem, which frees up the time to go deep on whatever makes that question hard. The goal is not to invent novel solutions to problems the industry solved decades ago. It is to recognize the pattern, apply what you already know, and focus on the decisions that matter.

The eight patterns

Each pattern has its own page covering the problem, the solutions in the order you would reach for them, the trade-offs an interviewer will probe, technologies, when not to use it, and an interview script.

PATTERN 01

Scaling Reads

Reads outgrow what your database can serve. Indexes, replicas, caches and CDNs, and the staleness each one brings.

Signal: feeds, catalogues, "mostly browsing" PATTERN 02

Scaling Writes

Replicas don't help writes. Shard the data, choose a shard key, understand consistent hashing, and absorb bursts.

Signal: likes, views, events, telemetry PATTERN 03

Dealing with Contention

Many users change the same data at once. Conditional writes, locks, optimistic concurrency control, and what changes across databases.

Signal: last ticket, bidding, booking, matching PATTERN 04

Handling Large Blobs

Move big files around without choking your servers: pre-signed URLs, chunked uploads, CDN downloads, and keeping metadata honest.

Signal: photos, videos, documents PATTERN 05

Long-Running Tasks

Work that outlasts a request. Queues, workers, job IDs, retries and dead letter queues, and when to stay synchronous.

Signal: transcoding, reports, bulk email PATTERN 06

Real-Time Updates

Tell the client the moment something happens. Polling, SSE, WebSockets, pub/sub, and routing with a consistent hash ring.

Signal: chat, notifications, live scores, progress bars PATTERN 07

Multi-Step Processes

Several services coordinating over hours or days. The saga pattern and durable workflow engines like Temporal and Step Functions.

Signal: checkout, onboarding, anything with "then wait for…" PATTERN 08

Proximity Search

Find things near a location. Why ordinary indexes fail in two dimensions, and geohash, quadtrees, S2 and H3.

Signal: "nearby", "within 2 miles", drivers, stores

Combining patterns: YouTube

In a real interview you will usually use several patterns at once. Take YouTube:

  • Uploading a video means large files: pre-signed URLs and chunked uploads.
  • Transcoding takes minutes, so it runs as a long-running task on a worker pool.
  • Progress reaches the uploader via real-time updates.
  • Coordinating everything from upload to publish is a multi-step process.
  • Once published, billions of views are a read-scaling problem.

How to use this in an interview

  1. Recognize. Match the requirement to a pattern using the signals above.
  2. Apply the standard solution. Start with the simplest rung of the ladder and say why you would escalate.
  3. Name the trade-offs. Every pattern has a characteristic cost: staleness, hot keys, lost ordering, duplicate delivery. Naming them before you're asked is a strong signal.
  4. Don't over-engineer. Several patterns come with a warning: don't shard before you need to, don't go async if the work takes 200 ms, don't reach for WebSockets before polling stops being enough, and don't build a geospatial index for a thousand rows.
  5. Go deep where the problem is unique. The time you save on the standard parts is what you spend on the genuinely interesting decisions.
