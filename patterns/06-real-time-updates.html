Real-Time Updates

HTTP is built so the client asks and the server answers. Real-time features need the opposite: the server must tell the client something the moment it happens. You solve it in two halves: how the update travels over the last hop to the client, and how it gets from whoever produced it to the server holding that client's connection.

Polling SSE WebSockets Pub/sub Consistent hashing

TL;DR

There are two separate problems, and interviewers like candidates who split them cleanly:

  1. Client-facing: how does the update reach the client? Climb this ladder only as far as you must: short polling (client asks every few seconds), long polling (server holds the request open until there is news), Server-Sent Events (one-way push over a long-lived HTTP response), WebSockets (a full-duplex connection).
  2. Server-side: how does the update reach the right server? The server where the event happens is usually not the server holding the user's connection. Decouple them with pub/sub: whoever has the update publishes it, and whoever holds the connection subscribes.
  3. Special case: heavy per-document state. For collaborative editing, game rooms and similar workloads, route every participant of one document to the same stateful server using a consistent hash ring, so state lives in one memory and updates apply in order.

Start with polling. It is boring, stateless, works through every proxy, and is often good enough. Reach for SSE or WebSockets only when latency or request volume proves polling is not enough, because persistent connections turn a stateless web tier into a stateful one and that costs real operational effort.

Recognize it when…
  • The prompt says chat, notifications, live scores, live comments, a live dashboard, a ride's moving dot on a map, or "show progress as it happens".
  • Users must see changes made by other users (or by background jobs) without refreshing.
  • Collaborative editing or multiplayer state is mentioned (Google Docs, Figma, a game lobby).
  • The requirement says "within a second" or "near real time", or a job's progress bar must update (see Long-Running Tasks).

The problem

Plain HTTP is request/response: a client sends a request, the server answers, the exchange is over. The server has no way to start a conversation. Yet many features need exactly that. A chat message arrives for Alice while she is looking at the screen. A video finishes transcoding and the progress bar should hit 100%. A goal is scored and a million viewers should see it within a second or two.

This breaks into two distinct difficulties:

Difficulty 1: the last hop to the client

The server cannot call the browser. The browser must keep some channel open, or keep asking. Each way of doing that has a different cost in latency, wasted requests, server memory, and compatibility with proxies and load balancers.

Difficulty 2: finding the right server

Once clients hold long-lived connections, each connection is pinned to one server in your fleet. Say Alice is connected to server 17 and Bob sends her a message through server 4. Server 4 has no connection to Alice. Somehow the message must travel from the server that learned about the event to the server that owns Alice's socket. With a hundred gateway servers and millions of users, "who holds Alice?" is a real routing problem.

Do the math out loud

Suppose 10M users are online at peak and each holds one connection. If one tuned gateway server can hold on the order of 50K to 100K mostly idle connections (the real number depends on memory per connection, kernel tuning and traffic, so hedge it), you need roughly 100 to 200 gateway servers for connections alone. Add a message rate: 10M users averaging one inbound message per minute is about 170K messages per second to route to the right gateway. That is why holding connections and routing messages are designed as two separate layers.

When it comes up

This pattern appears whenever freshness is a product feature rather than a nicety. Typical prompts:

  • Chat (WhatsApp, Slack, Messenger): deliver messages, typing indicators and read receipts instantly, including to users on many devices.
  • Notifications and live feeds: a badge count that ticks up, a new post appearing at the top of a timeline.
  • Live comments and reactions on a stream: huge fan-out to a few popular channels.
  • Live scores, stock tickers, auctions, ride tracking: many readers of the same fast-changing value.
  • Collaborative editing (Google Docs, Figma, Notion): every keystroke goes to every collaborator, in order, merged correctly.
  • Job progress: the transcoding or export progress bar from a long-running task.
  • Multiplayer games and shared whiteboards: per-room state with strict ordering.

Solutions, in escalation order

Steps 1 to 4 answer difficulty 1 (the last hop to the client). Steps 5 and 6 answer difficulty 2 (getting updates to the right server). Always start with the simplest step that meets the latency requirement.

Step 1Short polling

The client asks on a timer: GET /notifications?since=1042 every 3 to 10 seconds. The server answers immediately with whatever is new, usually an empty list. There is no special infrastructure. Every request is an ordinary, stateless HTTP call that any load balancer, CDN, proxy, firewall and framework already handles, and any server in the fleet can answer it.

  • Latency: on average half the poll interval, at worst the whole interval. A 5-second poll means updates show up 0 to 5 seconds late.
  • Waste: most responses are empty. 1M users polling every 5 seconds is 200K requests per second of mostly nothing, each paying for TLS, headers and an auth check.
  • Cheap tricks: use a cursor (since id, or ETag so unchanged answers are tiny 304s), slow down when the tab is hidden, add jitter so clients don't poll in lockstep, and serve the poll from a cache or a fast key lookup so empty polls cost almost nothing.

Pros

  • Trivial to build, test and debug
  • Stateless: scales like any read endpoint, can be cached
  • Works everywhere; no reconnection logic, no sticky routing
  • Survives deploys and server failures for free

Cons

  • Latency floor equal to the interval
  • Most requests return nothing
  • Load grows with users times poll rate, not with events
  • Poor fit for sub-second or chatty features

Polling is also the right answer for many job progress bars: the client polls GET /jobs/123 every couple of seconds, and nothing else is needed.

Step 2Long polling

Long polling keeps the HTTP request model but removes the empty answers. The client sends a request; if there is nothing new, the server does not answer yet. It parks the request until an event arrives or a timeout (typically 20 to 60 seconds) expires, then responds. The client processes the response and immediately sends the next request.

  1. Client: GET /events?cursor=88.
  2. Server finds nothing newer than 88 and holds the connection open, registering the waiting request.
  3. An event (id 89) occurs. The server completes the held request with it. Or the timeout fires and the server returns an empty 200/204.
  4. Client handles the data, then repeats from step 1 with cursor=89.

Latency becomes close to one network trip, because the server already has a request waiting. The cursor is what makes it safe: events that occur in the gap between one response and the next request are not lost, because the next request asks for "everything after 89".

  • Cost: the server now holds a pending request per client (memory, a file descriptor, a thread or async task). Under a thread-per-request server this is ruinous; an async server (Node, Netty, Go) copes well.
  • Overhead after each event: a new HTTP request with full headers each time, so a busy stream is chattier than SSE or WebSockets.
  • Compatibility: excellent. It is plain HTTP, but intermediaries may close idle connections, so keep the hold timeout shorter than the shortest proxy idle timeout in the path.
  • History: this is how many chat systems worked before WebSockets. It is a legitimate fallback, and libraries such as Socket.IO still downgrade to it when needed.

Step 3Server-Sent Events (SSE)

SSE is a standard way to keep one HTTP response open and stream events down it. The client creates new EventSource('/stream'). The server replies with Content-Type: text/event-stream and never ends the response, writing small text blocks whenever it has news:

HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache

id: 89
event: score
data: {"home":2,"away":1}

id: 90
data: {"minute":67}

: heartbeat comment (keeps proxies from closing the idle stream)

Events are separated by a blank line. The fields are data (payload, can span lines), event (a named type the client can listen for), id, and retry (how long the browser waits before reconnecting).

Why SSE is nicer than it looks

  • Automatic reconnection is built into the browser. If the connection drops, EventSource reconnects on its own and sends a Last-Event-ID header containing the last id it saw. The server can then replay everything after that id. You get resume-from-cursor semantics without writing client code.
  • It is just HTTP. Normal auth, normal logging, and HTTP/2 multiplexing, which removes the old browser limit of about six connections per origin on HTTP/1.1. (The native EventSource cannot set custom headers; use cookies or a fetch-based client if you need a bearer token.)
  • Simple server side: write text and flush. Proxies must not buffer the response (for example, disable response buffering in nginx for that route), and you should send a periodic comment line as a heartbeat.

Limits

  • One direction only. The client talks back with ordinary HTTP requests (POST /messages). That is fine for feeds, scores, notifications and progress, and awkward for high-frequency client-to-server traffic.
  • Text only (binary must be encoded, for example as base64).
  • Still a long-lived stateful connection to one server, so everything in the scaling sections below applies.
Underrated in interviews

If data flows only from server to client (live scores, a transcoding progress bar, notifications, a live comment feed), SSE is usually a better answer than WebSockets: simpler, plain HTTP, and free reconnection with Last-Event-ID. Saying "SSE is enough here, because the client never sends on this channel" shows judgment.

Step 4WebSockets

A WebSocket is a persistent, full-duplex TCP connection: either side can send a message at any time with very little per-message overhead. It starts as a normal HTTP request, then switches protocol.

How it works

  1. Handshake. The client sends a normal HTTP/1.1 GET with Upgrade: websocket, Connection: Upgrade and a random Sec-WebSocket-Key. The server replies 101 Switching Protocols with a hash derived from that key. Because it begins as HTTP, it uses ports 80/443 and can reuse your auth. Browsers cannot set arbitrary headers on the WebSocket constructor, so tokens usually travel in a cookie, a short-lived query-string ticket, or the first message.
  2. Frames. After the upgrade the connection is no longer HTTP. Data moves as small frames (text or binary) with a header of roughly 2 to 14 bytes, far less than an HTTP request's headers.
  3. Heartbeats. The protocol has ping and pong control frames. Idle TCP connections can die silently: NATs and load balancers drop idle flows, and a phone going through a tunnel never sends a FIN. So servers ping every 20 to 30 seconds (below the shortest idle timeout in the path) and close connections that do not answer. Applications often add their own heartbeat message too.
  4. Close. Either side sends a close frame with a status code, or the TCP connection simply dies.

What WebSockets do not give you

Unlike SSE, there is no built-in reconnect, no event ids and no replay. You (or a library such as Socket.IO, or a managed service) must build reconnection, resume cursors, message acknowledgements, channel multiplexing, and a fallback for networks that block upgrades. This is the "more infrastructure to get right" cost.

Pros

  • True bidirectional, very low latency
  • Tiny per-message overhead
  • Text and binary payloads
  • Fits chat, games, collaborative editing

Cons

  • Stateful connection: harder deploys and scaling
  • Needs WebSocket-aware load balancers, proxies and timeouts
  • You build reconnect, resume and acks yourself
  • Auth, authorization and abuse control are on you, per connection

When the user is not connected at all: mobile push

None of the above works when the app is closed or the phone is asleep, because the OS kills your connection. For that, hand the message to the platform push services: APNs (Apple) and FCM (Google, used for Android and web push). Your server sends a small payload to them, and the OS wakes the app or shows a notification. A typical design: if the user has an active connection to a gateway, push over it; otherwise fall back to APNs/FCM. Push is best-effort and size-limited, so treat it as a nudge to open the app and fetch the real data.

Step 5Pub/sub: getting the update to the right server

First, why connections change your architecture

A normal web request occupies a server for milliseconds. A WebSocket or SSE connection occupies it for hours. That has consequences:

  • Connections are long-lived and stateful. Each one holds a socket, buffers, TLS state and some application state (who the user is, which rooms they joined). A well-tuned async server (Netty, Go, Node, Erlang) can hold tens to hundreds of thousands of mostly idle connections; the real limit depends on memory per connection, message rate and kernel tuning, so measure rather than quote.
  • Separate the connection tier from business logic. Run a dedicated gateway (connection server) tier that only terminates sockets, authenticates, and shuttles messages. Chat logic, storage and fan-out decisions live in ordinary stateless services behind it. Then you can deploy business logic freely without dropping millions of sockets, and scale the two tiers independently.
  • Load balancing differs. The LB must support the upgrade: an L4 (TCP) balancer passes the stream through untouched, while an L7 (HTTP) balancer must understand Upgrade and keep the connection open. Raise idle timeouts well above your heartbeat interval (many LBs default to 60 seconds or less). Use "least connections" rather than round robin so new sockets go to the least loaded gateway. Sticky sessions are not required for connections themselves: a client connects once and stays on that server. They only matter if you rely on server-local state, which the pub/sub design avoids.
  • Deploys are disruptive. Restarting a gateway drops every connection on it, and all of those clients reconnect at the same moment. Treat this as a first-class concern (see "Operating it" below).

The routing problem and the pub/sub answer

With many gateways, the server that produces an event (the chat API that received Bob's message) is usually not the gateway that holds Alice's socket. Rather than have every service know the fleet topology, insert a publish/subscribe layer between them:

  1. When a client connects to a gateway, the gateway subscribes to the channels that client cares about: user:alice, room:42, doc:abc.
  2. Whoever has an update publishes it to the channel: PUBLISH user:alice {...}. The publisher neither knows nor cares how many gateways exist or which one holds Alice.
  3. The pub/sub system delivers the message to every gateway subscribed to that channel. Each gateway writes it to the matching local sockets.
  4. When the last local client for a channel disconnects, the gateway unsubscribes.

Choosing the pub/sub layer

Pub/sub (every subscriber gets every message) is a different model from a work queue (each message goes to one worker). The two are compared, along with Kafka vs RabbitMQ, in Long-Running Tasks.

  • Redis Pub/Sub: extremely fast and simple, but fire-and-forget. If a subscriber is disconnected or slow when a message is published, the message is simply gone, and nothing is stored. Fine for ephemeral signals (typing indicators, presence, cursor positions) or when durability lives elsewhere.
  • Redis Streams, Kafka, Kinesis, Google Pub/Sub, SNS+SQS: durable logs or queues. Messages are persisted and can be replayed from an offset, which supports catch-up after a reconnect. Kafka suits very high throughput, but one topic per user does not scale, so you partition by user or room id and have gateways filter. Per-subscriber queues (SQS-style) can give each gateway its own mailbox.
  • NATS: lightweight, very fast subject-based messaging with cheap, dynamic subscriptions (JetStream adds persistence).
  • Pick by need: ephemeral, low-latency fan-out favours Redis or NATS; "must not lose it" favours a durable log, usually together with a database as the source of truth.

Alternative: a connection registry

Instead of publishing to a channel everyone can subscribe to, keep a registry mapping each user to the gateway holding their connection, for example in Redis: SET conn:alice gateway-17 EX 60, refreshed by heartbeats. To deliver, the sender looks up the user's gateway and sends the message directly to that one (RPC, or a per-gateway queue or channel).

Per-user, per-room, and very large fan-out

  • Per-user channels (user:alice) are ideal for notifications and 1:1 chat: a gateway subscribes once per connected user. Cost: millions of tiny subscriptions, so pick a broker that makes subscriptions cheap (Redis and NATS do).
  • Per-room channels (room:42) suit group chat and shared documents. A gateway subscribes once per room no matter how many of its local clients are in it, then fans out locally over sockets. This is why the pub/sub fan-out costs scale with the number of gateways, not the number of users.
  • Fan-out on write vs on read. For a small group, the sender (or a service) can publish a copy to each member's channel (fan-out on write): simple, low read cost. For a room with millions of members, copying a message per member is too expensive; publish once to the room channel and let each gateway fan out locally (fan-out at the edge, closer to "on read"). Celebrity feeds make the same trade as in a news-feed design: write fan-out for ordinary users, read-time or edge fan-out for huge audiences.
  • Live-stream comment firehose. A stream with 1M viewers and thousands of comments per second cannot show every comment to every viewer. Sample or rate-limit what is delivered, batch many messages into one frame every 100 to 500 ms, drop low-value events under load, and send only the latest value for things like viewer counts ("last value wins"). Humans cannot read 5,000 comments per second anyway.

Delivery guarantees: what happens when something is missed

Pub/sub gives you speed, not safety. A gateway can be restarting, a phone can be in a tunnel, a broker can drop a message. Decide explicitly what guarantee each feature needs:

  • At-most-once (fire and forget): Redis Pub/Sub, UDP-like semantics. Right for typing indicators, cursors, presence blips, where a lost message is replaced by the next one a moment later.
  • At-least-once: store first, then deliver, retry until acknowledged. Messages may arrive twice, so the client must deduplicate by message id. This is the usual choice for chat and notifications.
  • Exactly-once delivery is not realistic end to end; you get "at-least-once plus idempotent handling" and call it effectively-once.

The reliable pattern: durable store plus "last seen id" catch-up

The robust design treats the real-time channel as a hint and the database as the truth:

  1. The producer first writes the message to a durable store (database or log) and gets a monotonically increasing sequence number or message id per conversation (a per-room counter, a Kafka offset, or a time-ordered id).
  2. Then it publishes over pub/sub for instant delivery to connected clients.
  3. The client keeps the last id it has seen. Each incoming message carries its id, so the client can detect a gap (it got 90 then 93).
  4. On a gap, or after any reconnect, the client asks the durable store: "give me everything after 90" (this is exactly what SSE's Last-Event-ID does). Missed messages are filled in from the database, in order.
  5. The client acks receipt (or simply advances its cursor). Unacked messages can be retried, or fall back to mobile push. The client drops duplicates it already has.

This way a lost pub/sub message costs a slightly delayed delivery, never a lost message. Ordering is preserved per conversation if ids are assigned per conversation, and the client applies messages in id order (buffering out-of-order arrivals briefly). Global ordering across all conversations is almost never needed and is very expensive.

Operating it: the failure modes that bite

  • Presence and heartbeats. "Online" is inferred, not known. Clients or servers send heartbeats; the registry entry (presence:alice) carries a TTL refreshed on each one; no heartbeat means offline after the TTL. Debounce presence changes (a flapping mobile connection should not spam every friend), and broadcast presence lazily or only to users who are looking.
  • Reconnection storms. When a gateway dies or is deployed, its 100K clients all reconnect within seconds, hammering the load balancer, auth service and database (a thundering herd). Clients must reconnect with exponential backoff plus random jitter, not a fixed retry delay. The server can also tell clients a randomised "come back in N seconds" when draining, and rate-limit connection accepts.
  • Graceful deploys and draining. To roll a gateway: remove it from the load balancer so it takes no new connections, send clients a "reconnect elsewhere" message with a jittered delay, let the connections drain over minutes, then stop it. Roll one small batch at a time so the rest of the fleet absorbs the reconnects.
  • Authentication and authorization on connect. Authenticate during the handshake (cookie, short-lived ticket token) and authorize every subscription: may this user join room:42? Re-check or expire the session on long-lived sockets, since a token that was valid at connect time may be revoked hours later. Validate message size and rate to resist abuse.
  • Backpressure and slow consumers. A client on a bad network cannot drain its socket as fast as you publish. Without limits, per-connection buffers grow until the gateway runs out of memory. Give each connection a bounded outbound queue; when it fills, drop low-priority messages, collapse updates to the latest value, or disconnect the slow client and let it catch up via its last seen id on reconnect. Never let one slow client block the loop that serves the others.
  • Hot channels. One popular room or celebrity channel puts load on one broker partition or Redis shard. Spread by sharding the channel (room:42#0..N), batching, or moving the hot channel to its own infrastructure.

Step 6Stateful routing with a consistent hash ring

Why pub/sub is the wrong tool here

Pub/sub is perfect when an update is cheap to forward: a chat message is stored and relayed as is. But some workloads need the server to process every update against in-memory state before anyone else sees it:

  • Collaborative editing (Google Docs, Figma): two people type at the same spot at the same moment. Someone must merge those edits into one agreed document, in a single order.
  • Multiplayer game rooms: one authoritative simulation per match decides who hit whom.
  • Any per-document or per-room state held in memory for speed: a live auction, a shared whiteboard, a collaborative spreadsheet.

If you spread such a document's users over many gateways and merge through pub/sub, every server would have to load the document, run the merge logic on every update, and agree on ordering, which needs distributed locks or consensus on the hot path. That is slow, wasteful (the same heavy work repeated N times) and fragile. The cleaner trick is to make the problem local: send every user of document D to the same server. That server keeps D in memory, applies updates one after another in the order it receives them (no locks, because there is a single writer), persists them, and broadcasts the results to the document's connected clients.

The question becomes: how do all clients of D reliably find "D's server", and what happens when servers come and go? A consistent hash ring answers both.

How the ring routes documents

This is a focused recap; the full treatment, including why naive hash(key) % N breaks, lives in Scaling Writes.

  1. Imagine a circle of hash positions (for example 0 to 264-1 wrapping around). Hash each server (by its id or address) onto the ring.
  2. Hash the documentId onto the same ring. The document is owned by the first server found moving clockwise from its position.
  3. The router (or the gateway itself) holds the current list of servers, so it computes the owner locally with a binary search over sorted positions. There is no lookup service on the hot path: no extra hop, no central bottleneck.
  4. The client connects (WebSocket) to its document's owner, or connects to any gateway that forwards to the owner. All clients of D hash to the same position and so land on the same server.

When servers join or leave

  • Add a server: it lands at a new position and takes over only the arc between itself and the previous server. Documents on that arc change owner; every other document stays put. (With modulo hashing nearly everything would move.)
  • Remove or lose a server: its arc falls to the next server clockwise. Clients of the affected documents see their connection drop, reconnect (with jittered backoff), get routed to the new owner, and that owner loads the document's state from the database or operation log and rebuilds memory. In-memory state is a cache of durable state, so the server must persist updates (or at least a write-ahead log) as it goes.
  • Virtual nodes: a few servers placed once each leave uneven arcs, so one server may own twice the load of another. Place each physical server at many positions (for example 100 to 256 virtual nodes). Arcs even out, and when a server dies its load is spread across all the others rather than dumped on a single neighbour.

What to watch for

  • Membership must be agreed. Router and servers need a consistent view of who is alive. Use a coordination service (ZooKeeper, etcd, Consul) or gossip (as in Cassandra and many actor systems). Views will briefly disagree.
  • Dual ownership during rebalancing. For a moment, the old owner may still think it owns document D while the new owner has taken over (a stale view, a network partition, a long GC pause). Two writers corrupt the document. Protect with an epoch (fencing token): each ownership change increments a number, every write to the store carries it, and the store rejects writes with an older epoch. Alternatively take a short lease in etcd or ZooKeeper before accepting writes for D.
  • Hot documents. Hashing balances documents, not load. One viral document with 50,000 live viewers still sits on one server. Cap collaborators per document, send the huge read-only audience through the pub/sub fan-out path (editors on the owner, viewers on ordinary gateways), and watch for it in metrics.
  • Memory and eviction. Unload idle documents after a timeout, and snapshot state periodically so loading does not mean replaying a long history.
  • Gateway tier and ring tier can be the same or separate. Simplest: clients connect through a stateless gateway that hashes the documentId and proxies the socket to the owner. Separate tiers keep deploys of editing servers from dropping every client connection directly.

Pros

  • Single writer per document: ordered updates with no distributed locks
  • State lives in memory: very low latency
  • Routing is computed locally, with no lookup service
  • Scaling out moves only a small fraction of documents

Cons

  • Stateful servers: deploys, failover and rebalancing need care
  • Needs membership, fencing and state reload on handoff
  • Load balances by document count, not real load; hot documents hurt
  • More moving parts than plain pub/sub

Tiny primer: how collaborative editing merges changes

Operational Transformation (OT), used by Google Docs, has a central server order the operations; when two concurrent operations conflict (both insert at position 5), the server transforms one against the other so that applying them in either order gives the same text. It needs that single authoritative server, which is exactly why a hash ring that pins each document to one owner fits it so well. CRDTs (Yjs, Automerge) design the data structure so that concurrent edits commute and merge automatically in any order, so they tolerate peer-to-peer and offline editing and do not strictly need one owner; but they still benefit from a server that persists, relays and compacts the document. Either way, one owner per document makes the system simpler.

Trade-offs & pitfalls

Real-time features are easy to demo and hard to run. These are the characteristic failure points, and the fix for each.

Statefulness vs simplicity

Every persistent connection ties a client to one server. You gain latency and lose easy deploys, easy autoscaling and free failover. Polling gives the reverse. Choose the least stateful mechanism that meets the latency requirement.

Push is a hint, the database is the truth

Connections drop, messages get lost, clients sleep. Design so that missing a push never loses data: persist first, publish second, and let any client rebuild its state with "give me everything after id N" on connect and on suspected gaps.

Reconnection storms

A deploy, a crashed gateway or a network blip makes a whole tier of clients reconnect at once. Without jittered exponential backoff, drain-based rolling deploys and accept-rate limits, the reconnect wave itself takes down the auth service or database.

Slow consumers and memory

Unbounded outbound buffers turn one bad network into a gateway out-of-memory crash. Bound every queue, coalesce or drop low-value updates, and disconnect clients that cannot keep up.

Fan-out cost

The cost of one event is its audience size. Ordinary rooms can use per-member delivery; huge audiences need publish-once with edge fan-out, batching and sampling. Do not promise to deliver every event to every viewer of a mega-stream.

At-most-once vs durable

Redis Pub/Sub is fast but forgets. Using it alone for messages that must arrive loses them silently. Pair it with a durable store, or use a log-based broker, when loss matters.

Stateful ring pitfalls

Dual ownership during rebalancing (fix with epochs/fencing), hot documents (cap collaborators, offload readers to pub/sub), and slow state reloads after a failover (snapshots plus a log).

When NOT to use it

  • Start with polling. If a few seconds of delay is acceptable, polling is the correct answer, not a stepping stone you apologise for. A job-progress bar polled every 2 seconds is a perfectly good design.
  • Don't reach for WebSockets until polling genuinely stops being enough. "Real-time" in a requirements doc often means "a few seconds". Persistent connections cost you stateful servers, special load balancer settings, reconnect logic and harder deploys. Ask what latency the product truly needs and measure whether polling load is actually a problem.
  • One-way data does not need WebSockets. Use SSE for feeds, scores and progress.
  • Don't build the hash ring for cheap updates. If updates can be forwarded as is (chat, notifications), plain pub/sub is simpler. The ring is for heavy per-document processing with in-memory state.
  • Rarely-changing data belongs in a cache or CDN (see Scaling Reads), not a live stream.
  • Mobile apps in the background cannot hold your socket. Use APNs/FCM for those, not connection tricks.

Interview script

Say it like this
"For delivery to the client I'd start with polling, since a few seconds of latency is acceptable for the progress bar and it keeps the web tier stateless. For chat I need push, so I'd use WebSockets: the client opens one connection to a gateway tier whose only job is holding sockets, authenticating and heartbeating. The catch is that the server that receives Bob's message isn't the one holding Alice's socket, so I'd put pub/sub between them: the chat service writes the message to the database with a per-conversation sequence number and publishes to Alice's channel, and whichever gateway holds her connection is subscribed and pushes it. Pub/sub can drop messages, so the client tracks the last id it saw and, after any gap or reconnect, fetches everything after it from the database, deduplicating by id. Clients reconnect with jittered backoff so a gateway deploy doesn't cause a stampede. For collaborative editing, where every update needs heavy in-memory merging, I'd instead route every user of a document to one server with a consistent hash ring over the documentId, so there is a single writer per document, with an epoch to fence off stale owners during rebalancing."

Deep-dive Q&A

Why not just use WebSockets for everything?

Because each connection pins a client to a server, which makes the tier stateful: harder deploys (draining), harder load balancing, reconnect storms, and you must build resume and acks yourself. If updates are one-way, SSE gives you push with automatic reconnect over plain HTTP. If a few seconds is fine, polling needs none of it. WebSockets are right when the client sends frequent messages too and latency matters: chat, games, editing.

Alice is connected to gateway 17; Bob's message arrives at gateway 4. How does it reach her?

Gateway 4 (or the chat service behind it) stores the message, then publishes to a channel for Alice (or the conversation). Gateway 17 subscribed to that channel when Alice connected, so the broker delivers it there and the gateway writes it to her socket. Alternatively, look up Alice in a connection registry (conn:alice = gateway-17) and send it to that gateway directly. If she is not connected, skip the socket and use APNs/FCM; she catches up from the database when she opens the app.

Redis Pub/Sub dropped a message while a gateway was restarting. How do you avoid losing it?

Never rely on the pub/sub message as the record. Persist the message first with a monotonic per-conversation id, then publish. Clients remember the last id they saw; on reconnect (or when they see a gap in ids) they request everything after that id from the durable store. Duplicates are dropped by id. A durable broker (Kafka, Redis Streams) can also replay from an offset, but the "persist then notify, client catches up" structure is what gives the guarantee.

A gateway holding 100K connections is deployed. What goes wrong and how do you prevent it?

All 100K clients reconnect at once, hitting the load balancer, auth and database together, and may cascade into other gateways. Prevent it with draining (remove from LB, tell clients to reconnect after a random delay, drain slowly), rolling one small batch at a time, client exponential backoff with jitter, accept-rate limiting on gateways, and making the reconnect path cheap (cached auth, no heavy queries on connect).

Why use a consistent hash ring for Google Docs instead of pub/sub?

Each edit must be merged against the document's current state and ordered consistently. With pub/sub and arbitrary gateways, every server would repeat the merge, and you would need distributed coordination to agree on the order. Routing all collaborators of a document to one owner lets that server hold the document in memory and apply edits one at a time, a single writer with no locks. The ring decides the owner by hashing the documentId, computed locally by the router, and adding or removing servers only moves a small arc of documents. The costs are state reload on handoff, fencing against dual ownership, and hot documents.

What happens to a document when its owner server crashes?

Membership (ZooKeeper/etcd/gossip) detects the failure, the ring is updated, and the document's arc passes to the next server clockwise. Clients reconnect with backoff and are routed to the new owner, which loads the latest snapshot plus the operation log from durable storage and resumes. Edits that were only in the dead server's memory are lost unless they were persisted before being acknowledged, so write ahead to the log first. An epoch number on every write prevents the old owner, if it is only partitioned rather than dead, from writing stale data afterwards.
