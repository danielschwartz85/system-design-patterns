Scaling Writes

Replicas copy data, so they cannot absorb more writes. When one database can't keep up, you split the data across machines (sharding), pick a storage engine built for writes, and smooth out bursts with queues, load shedding and batching.

Write-heavy apps Sharding Consistent hashing Queues & batching

TL;DR

Reads can be cached and copied; writes cannot. Every write has to reach durable storage and be applied by every copy of that data. So the strategy changes: instead of copying the data, you split it, and instead of writing eagerly, you buffer and combine. In escalation order:

  1. Scale the single node first: bigger machine, fewer indexes, batched inserts, tuned commit settings.
  2. Shard: partition the data across several databases by a shard key, so each machine takes only a slice of the writes. Choosing the shard key is the real design decision.
  3. Use a write-optimized store (LSM-tree databases such as Cassandra, ScyllaDB, DynamoDB, or an append-only log) when the workload is mostly inserts.
  4. Handle bursts with a queue to absorb the spike, load shedding to drop the least important writes, and batching to do far less work per write. A queue only buys time: if the spike never ends, it grows forever.

Sharding has a famous sub-problem: how to map keys to machines so that adding or removing a machine does not reshuffle everything. That is consistent hashing, covered in depth below.

Recognize it when…
  • Every user action is a write: posts, likes, views, clicks, GPS pings, sensor readings, chat messages, log lines.
  • The prompt gives a write rate that is clearly beyond one machine (tens of thousands of writes per second and up), or a dataset too large for one disk.
  • There is a sudden surge: a Super Bowl ad, a flash sale, a product launch, a viral post.
  • Someone proposes "just add read replicas" and the bottleneck is actually writes.
  • Counters (likes, views, impressions) are updated by millions of users on a small number of popular items.

The problem

Take a social app. Every post is a write. Every like is a write. Every view you count is a write. A single post that goes viral can collect millions of likes within minutes, and a modest feature like "view counts" turns every page load into an update.

One database server has a hard ceiling on write throughput. Every write must be appended to the write-ahead log (WAL) and flushed to disk for durability, applied to the table, and applied to every index on that table. Once the disk, the CPU, the lock manager, or the single-writer replication stream saturates, writes start queueing, latency climbs, connection pools fill, and the app falls over, including the reads.

The tempting fix from Scaling Reads does not work here. A replica is a follower that replays every change made on the primary. Adding replicas adds read capacity, but each one must still apply 100% of the writes, so the write capacity of the system stays exactly that of one machine (and replication adds a little overhead on top).

Do the math out loud

Example: 100M daily users, each generating about 20 write events a day (likes, views, posts) is 2B writes/day, roughly 23K writes/second on average, and perhaps 3 to 5 times that at peak, so 70K to 120K/s. A well-tuned single relational database can handle on the order of thousands to a few tens of thousands of simple writes per second (the exact figure depends heavily on hardware, row size, indexes and durability settings). So at this scale you must plan to split the writes. State the numbers, then state which pattern they trigger.

When it comes up

Any design where data is created faster than it is consumed. Typical prompts:

  • Social feeds with likes, comments and views (Instagram, Twitter/X, TikTok): enormous counter updates.
  • Ride-hailing and delivery: every driver sends a location ping every few seconds.
  • Metrics, logging and analytics ingestion: millions of events per second, append-only.
  • Chat and messaging (WhatsApp, Slack): each message is a write, plus delivery and read receipts.
  • IoT and telemetry: huge numbers of devices reporting continuously.
  • Ad click and impression tracking: bursty, high volume, and each event must be counted.
  • Ticketing and flash sales: a short, violent spike (this also overlaps with Contention).

Solutions, in escalation order

As with reads, start with the cheapest thing that could work. The steps below add progressively more operational complexity, and sharding in particular is hard to undo.

Step 0Scale up one node first

Before you split anything, check how much one machine can really do. This is the answer interviewers want to hear first, because it shows judgment: sharding is expensive, so you earn it with numbers.

  • Bigger hardware: more cores, more RAM (so the working set and index pages stay in memory), NVMe SSDs with high write IOPS, and fast network. Modern cloud instances offer many terabytes of RAM and tens of thousands of IOPS.
  • Make each write cheaper: drop indexes you don't need (each index is another structure to update on every write), use multi-row inserts or COPY/bulk loading, use a connection pooler, keep rows narrow, and avoid hot-row updates in transactions.
  • Relax durability where the business allows: group commit and relaxed fsync settings (for example PostgreSQL synchronous_commit = off) trade a small window of possible loss for much higher throughput. Never do this for money.
  • Partition tables within the node: time-based partitioning keeps recent data and its indexes small and makes old data cheap to drop.
  • Separate the write path from everything else by moving analytics queries and reporting to a replica, so they stop competing with writes.

Where it ends: vertical scaling hits a ceiling (the biggest machine you can buy), cost grows faster than capacity, and one machine remains a single point of failure with one WAL and one set of disks. When your numbers say one node cannot do it, move on.

Step 1Sharding: split the data

Sharding (horizontal partitioning) splits one logical dataset across several independent databases, called shards. Each shard owns a subset of the rows and handles only the writes for them. If you have 10 shards and the load is even, each takes about one tenth of the writes, so capacity grows roughly linearly as you add shards. As a bonus, each shard holds a fraction of the data, so storage and index sizes shrink too.

Each shard is itself usually replicated (a primary plus followers) for availability. Sharding scales writes; replication within each shard gives durability and read capacity. They are complementary.

Two decisions define a sharded system: what is the shard key (which field decides placement) and what is the strategy (how a key value maps to a shard).

  • Smaller shards are faster to back up, index and recover
  • Failures are contained: one shard down affects only its slice

Cons

  • Queries that don't include the shard key must hit every shard
  • Multi-shard transactions and joins are slow or unsupported
  • Poor shard keys create hot shards
  • Resharding is operationally painful
  • More moving parts: routing, monitoring, schema migrations on N databases

Consistent hashing: why and how

Hash sharding sounds trivial: shard = hash(key) % N. It breaks the moment N changes, and in a system that grows or loses machines, N always changes. Consistent hashing is the technique that fixes this, and it is one of the most commonly asked-about building blocks in distributed systems interviews.

1. Why it exists: the problem with hash(key) % N

Say you have 12 keys numbered 0 to 11 and use key % N as the shard. Compare the shard each key lands on with N = 3 shards and then with N = 4, after a fourth shard is added:

Key01234567891011
Shard with N = 3012012012012
Shard with N = 4012301230123
Moved?nononoyesyesyesyesyesyesyesyesyes

Only keys 0, 1 and 2 stay put: 9 of 12 keys (75%) move. In general, going from N to N+1 shards remaps about N/(N+1) of all keys, which approaches 100% as N grows. The ideal is much smaller: a new shard should take over only its fair share, about K/(N+1) of the K keys (here 3 of 12, the keys that land on the new shard 3, and nothing should move between the old shards).

The consequences of modulo hashing at scale are severe:

  • Massive data migration: three quarters of your data must be copied between machines just to add one node, while serving traffic.
  • Cache-miss storms: if the shards are cache servers, nearly every lookup suddenly goes to the wrong node and misses, and the backing database takes the entire load at once.
  • A failure looks the same as a resize: losing one node changes N, so a single machine crash remaps almost everything.

The goal of consistent hashing: when a node is added or removed, only about K/N keys (the keys that belong to that node) should move, and no key should move between two nodes that both survive.

2. How it works

  1. Build the ring. Take the output space of a hash function, for example 0 to 232-1 (or 264-1), and imagine it bent into a circle, so the largest value wraps around to 0.
  2. Place nodes on the ring. Hash each node's identifier (name, IP) to get its position.
  3. Place keys on the ring. Hash each key with the same function to get its position.
  4. Lookup rule: a key is owned by the first node you meet moving clockwise from the key's position (wrapping past the top if necessary). Equivalently, each node owns the arc between its predecessor and itself.

Finding the owner is a binary search over the sorted list of node positions, so a lookup is O(log N) and needs no central coordinator: every client or server with the same node list computes the same answer.

Worked example on a tiny ring (positions 0 to 99)

Three nodes: A = 10, B = 40, C = 70. That gives these arcs: A owns 71 through 99 and 0 through 10 (the arc wraps around the top), B owns 11 through 40, C owns 41 through 70. Six keys hash to 5, 25, 33, 48, 62 and 85.

Adding a node. Now add D = 55. D lands in the arc that C used to own entirely (41 to 70). Walking clockwise, D now catches every key between its predecessor B (40) and itself (55). The only key in 41 to 55 is key 48, so key 48 moves from C to D. Key 62 is past D, so it still belongs to C. Keys 5, 25, 33 and 85 are unaffected. Exactly one arc changed hands, and it came from exactly one neighbor (the clockwise successor, C).

Removing a node. Go back to the original three-node ring and suppose B dies. B's arc (11 to 40) is absorbed by its clockwise successor C, so keys 25 and 33 now belong to C. Keys 5, 48, 62 and 85 do not move. Nothing is reshuffled between A and C. The mirror-image rule holds: when a node leaves, only that node's keys move, all to one neighbor.

Notice that D took 15 of the 100 positions rather than the ideal quarter, because the arcs were unequal to begin with. That is the weakness the next section fixes.

3. Virtual nodes (vnodes)

With only a few nodes on the ring, positions are essentially random, so arcs are very uneven: one node may own 45% of the ring and another 10%. That gives uneven load. Worse, when a node fails, its whole arc dumps onto a single clockwise neighbor, which may then be overloaded and fail too (a cascading failure).

Solution: give each physical node many positions on the ring. Instead of hashing "node-A" once, hash "node-A#0", "node-A#1", … "node-A#127" and place all of them. Each of these is a virtual node. A physical node's data is the union of many small arcs scattered around the ring. Typical counts are in the range of 100 to 256 per node (Cassandra historically defaulted to 256 tokens per node, and newer versions default to fewer, with smarter token allocation).

  • Even load: by the law of large numbers, the sum of many random small arcs is close to 1/N of the ring. Imbalance shrinks roughly with the square root of the number of vnodes.
  • Heterogeneous hardware: give a machine with twice the capacity twice as many vnodes and it takes twice the load.
  • Failures and joins spread out: when a node dies, each of its many small arcs falls to a different successor, so the load is shared across many peers rather than one. When a node joins, it takes small slices from many existing nodes, so the data streams in from many sources in parallel and recovery is fast.
  • Cost: more metadata (the ring has N times V entries), more complicated repair and streaming, and some operations (like range scans or repair) touch many small ranges.

4. Replication on the ring

Consistent hashing also gives a natural way to replicate. To keep R copies of a key (commonly R = 3), store it on the key's owner and the next R-1 distinct physical nodes clockwise. This list is called the preference list in the Dynamo paper. With vnodes, consecutive ring positions can belong to the same machine, so the walk must skip vnodes that map to a physical node already in the list (and real systems also try to spread replicas across racks or availability zones). When a node is down, systems like Dynamo use hinted handoff: the next healthy node temporarily holds the write and hands it back when the original owner returns.

Code: a ring lookup with vnodes

import bisect, hashlib

def h(s):                      # any uniform hash works (murmur3, xxhash)
    return int(hashlib.md5(s.encode()).hexdigest(), 16) % 2**32

class Ring:
    def __init__(self, vnodes=128):
        self.vnodes = vnodes
        self.points = []       # sorted ring positions
        self.owner = {}        # position -> physical node

    def add(self, node):
        for i in range(self.vnodes):
            p = h(f"{node}#{i}")
            bisect.insort(self.points, p)
            self.owner[p] = node

    def remove(self, node):
        self.points = [p for p in self.points if self.owner[p] != node]
        self.owner = {p: n for p, n in self.owner.items() if n != node}

    def lookup(self, key):
        # first ring position at or after hash(key), wrapping around
        i = bisect.bisect_left(self.points, h(key)) % len(self.points)
        return self.owner[self.points[i]]

    def preference_list(self, key, r=3):
        # next r DISTINCT physical nodes clockwise (skip repeat vnodes)
        i = bisect.bisect_left(self.points, h(key))
        nodes = []
        for step in range(len(self.points)):
            n = self.owner[self.points[(i + step) % len(self.points)]]
            if n not in nodes:
                nodes.append(n)
                if len(nodes) == r:
                    break
        return nodes

5. Where it is used, and the alternatives

  • Amazon Dynamo (the 2007 paper that popularized it), and its descendants Cassandra, Riak and ScyllaDB use a ring with vnodes and a preference list for replication. DynamoDB, the managed service, descends from these ideas but is a different system, so don't claim it exposes a ring.
  • Distributed caches: the memcached client library "ketama" popularized consistent hashing so that adding a cache node doesn't invalidate the whole cache. Sharded Redis clients do similar things.
  • Load balancers and CDNs: to send the same client or object to the same backend (cache affinity, session stickiness). Envoy offers a "ring hash" policy, and Google's Maglev uses a lookup-table variant with similar goals.
  • Stateful service routing: chat or WebSocket servers, where one user or room must always land on the same server (see Real-Time Updates).

6. Caveats

  • It balances keys, not load. A celebrity key is still one key on one node, however nicely the ring is balanced. Hot keys need separate mitigation (see below).
  • Membership must be shared. Every router needs the same view of the ring, or two clients will disagree about who owns a key. Spread it with a gossip protocol (Cassandra, Dynamo) or keep it in a coordination service such as ZooKeeper or etcd, or a central coordinator with clients caching and refreshing the map.
  • The data still has to move. Consistent hashing tells you which keys move (a small fraction), not how to move them safely. The new node must stream its arc from the old owner (bootstrap), and reads and writes must be handled correctly during the handoff.
  • It is about placement, not consistency. It says where a key lives. Whether replicas agree is a separate question, answered by quorums, leader election or consensus.
  • Hash function quality matters. Use a uniform, fast, non-cryptographic hash (murmur3, xxhash), and the same one on every client.
If asked: why consistent hashing?
"With hash mod N, changing N remaps almost every key, so adding one shard triggers a huge data migration and, for caches, a miss storm. Consistent hashing places nodes and keys on the same hash ring, and each key belongs to the first node clockwise. Adding or removing a node then moves only about K over N keys, only to or from its neighbor. I'd use many virtual nodes per machine so load is even and a failed node's data spreads across many peers, and replicate each key to the next R distinct nodes. It solves placement, not hot keys or consistency, so I'd still handle those separately."

Choosing the shard key

The shard key decides everything: how evenly load spreads, which queries are cheap, and which are painful. A good key satisfies four properties:

  • High cardinality: many distinct values, far more than the number of shards. Sharding on a boolean or a status column can use at most a couple of shards.
  • Even distribution: values (and the traffic they attract) spread roughly uniformly. Sharding by country makes the China shard enormous while the New Zealand shard idles. Check for skew in both data size and request rate.
  • Matches the access pattern: the most frequent and most latency-critical queries should include the shard key, so each is served by a single shard.
  • Stable and not monotonic: the value shouldn't change after creation (moving a row between shards is expensive), and with range sharding it shouldn't increase over time (timestamps, auto-increment IDs concentrate all new writes on one shard).

For the social app, compare two candidates. Post ID hashes beautifully: writes spread evenly across all shards. But "show me all posts by user 42" now needs to query every shard and merge the results. User ID keeps one user's posts together so that query hits one shard, but a heavy user or a celebrity concentrates load on one shard, and likes on a popular post pile onto the author's shard. There is never a perfect shard key. It depends on the dominant access pattern, and saying so out loud, then choosing one with a justification, is exactly what the interviewer wants. A common compromise: shard posts by author (so profile views are single-shard) but shard the high-volume like and view events by post ID, and aggregate counters separately.

Cross-shard queries

Any query that cannot be routed by the shard key becomes a scatter-gather: the coordinator sends the query to every shard, waits for all responses, and merges them (sorting, applying LIMIT, aggregating). Costs grow with shard count, and latency is set by the slowest shard (tail latency amplification). Mitigations: keep the common queries on the shard key, precompute and store denormalized copies keyed by the other access pattern (for example a "posts by user" table sharded by user, alongside "posts by ID"), or use a search index for ad hoc queries.

Secondary indexes across shards

What about lookups on a non-shard-key column, such as finding a user by email? There are two designs:

  • Local (document-partitioned) index: each shard indexes only its own rows. Writes are cheap and consistent (one shard), but a query by that column must scatter-gather across all shards.
  • Global (term-partitioned) index: the index is itself sharded, by the indexed value. A lookup hits exactly one index shard, but every write now touches the data shard and an index shard, usually updated asynchronously (so the index can lag; DynamoDB's global secondary indexes work this way).

Cross-shard transactions

Atomically updating rows on different shards (for example moving money between two accounts on different shards) requires two-phase commit or a saga, both of which are slower and more fragile than a single-node transaction. Best practice: pick a shard key so that data that must change together lives together (all of a user's rows on one shard), and push the rest to patterns built for it. See Dealing with Contention for coordinating concurrent updates and Multi-Step Processes for sagas and workflows.

Resharding

Eventually the number of shards or their boundaries must change: data grows, or one shard turns hot. Resharding means copying data to new shards while the system keeps serving traffic, then switching routing atomically, then cleaning up. It is slow, risky and a classic source of outages. Ways to make it survivable:

  • Consistent hashing or fixed hash slots so that only a fraction of data moves.
  • Over-provision logical shards: create many more logical shards than machines (say 1,024 logical shards on 8 servers). Rebalancing then means moving whole logical shards between machines, never splitting them. This is what Redis Cluster slots, Kafka partitions and Elasticsearch shards effectively do.
  • Dual-write or change-data-capture to migrate online: backfill the new shards, stream ongoing changes, verify, then cut over reads and finally writes.
  • Use a database that does it for you (Vitess, Citus, CockroachDB, Spanner, DynamoDB, MongoDB's balancer).

Hot shards and hot keys

A balanced hash does not guarantee balanced load. A single popular key (a celebrity's post, a viral video, a hot product) receives so many writes that its shard saturates even though other shards are idle. Adding shards doesn't help, because the key still lives on exactly one of them. Mitigations:

  • Key salting (suffixing): split one hot key into N sub-keys, for example post:123#0 through post:123#9. Each write picks a random suffix, so the writes spread over up to N shards. The cost moves to reads: reading the total now means querying all N sub-keys and summing. Apply it only to keys known to be hot (detected by monitoring or a threshold), not to everything.
  • Write coalescing for counters: don't update the shared row per event. Aggregate in memory and write the sum periodically (see batching below). This often removes the hot key problem entirely, since a million likes become a few hundred updates.
  • Split hot ranges (range sharding): Bigtable, HBase, Spanner and CockroachDB automatically split a tablet or range that is too large or too busy.
  • Avoid monotonic keys in range-sharded stores: prefix timestamps or sequential IDs with a hash or bucket to avoid "all writes go to the latest range".
  • Isolate whales: use a directory to give a huge tenant or celebrity its own dedicated shard.
  • Managed help: some services (DynamoDB, for instance) adapt partition capacity to skew, but with per-partition throughput limits, so a single very hot key can still be throttled. Check the service's limits instead of assuming it is infinitely elastic.

Step 2Choose a write-optimized storage engine

Not every database is equally good at absorbing writes. The classic relational storage structure, the B-tree, updates pages in place: a write may need to read a page, modify it and write it back to a random disk location, plus the WAL. That is a lot of random I/O per write.

LSM trees (log-structured merge trees) turn random writes into sequential ones:

  1. Each write is appended to a commit log (for durability) and inserted into an in-memory sorted structure, the memtable. This is fast: one sequential disk append plus a memory update.
  2. When the memtable is full it is flushed to disk as an immutable sorted file (an SSTable), again sequentially.
  3. A background compaction process merges many SSTables into fewer larger ones, discarding overwritten and deleted values.
  4. Reads check the memtable and then possibly several SSTables, accelerated by Bloom filters (which cheaply say "this key is definitely not in this file").

The trade is clear: writes are cheap, but reads can touch more files, and compaction causes write amplification (data is rewritten several times in the background) and periodic I/O spikes. LSM engines power Cassandra, ScyllaDB, HBase, Bigtable, RocksDB and LevelDB (and many databases built on RocksDB). DynamoDB is another popular choice for high write volume on key-addressed data, though its storage internals are its own. They typically also give you built-in sharding by partition key, tunable replication and consistency, and linear scale-out, at the price of limited joins, limited ad hoc queries, and eventual consistency options.

The same principle applies to the extreme case: an append-only log such as Kafka does nothing but sequentially append records, which is why it can ingest very large volumes on commodity disks. Use it as the write path for event streams and process them downstream.

Pros

  • Very high sustained write throughput per node
  • Sharding and replication built in
  • Sequential I/O is gentle on SSDs and spinning disks
  • Natural fit for time-series, events, messages

Cons

  • Query model limited to the key and clustering columns you designed for
  • Weaker transactions; often eventual consistency
  • Compaction overhead, tombstones, read amplification
  • You must model your data around queries up front

Step 3Handle bursts: queue, shed, batch

Even a well-sharded system is sized for normal load. A Super Bowl ad, a flash sale or a viral post can send ten or a hundred times the usual write rate for a few minutes. You usually cannot (or do not want to) provision for the peak permanently, so you combine three tools.

Queues: absorb the spike

Put a durable queue between the API and the database (SQS or RabbitMQ are the simple defaults; a log such as Kafka, Kinesis or Pulsar if you also need replay or very high throughput). The API validates the request, appends it to the queue and immediately returns 202 Accepted. Consumers then drain the queue and write to the database at a steady rate the database can sustain. The queue converts a sharp spike into a smooth, longer stream. Writes are not lost if the database is briefly slow or down, because they wait in the queue. For the choice between a work queue and pub/sub, and between Kafka and RabbitMQ, see the deep dive in Long-Running Tasks.

  • Partition the queue by the same key as the database shards (or by an ordering key). That keeps per-key order and lets consumers scale out in parallel, up to the number of partitions.
  • Delivery is usually at-least-once, so consumers can see duplicates. Make writes idempotent (dedupe by an event ID, or use upserts).
  • The write is now asynchronous. The user may not immediately see their own write. Use optimistic UI, or return an ID they can poll. Long jobs behind a queue are the subject of Long-Running Tasks.
  • Monitor consumer lag (how far behind the consumers are) and queue age. That is your signal for how much headroom you have left.

The limit of a queue. It only buys time. Suppose a spike brings 50,000 writes/second for 10 minutes into a system whose database can handle 10,000/s. The backlog grows by 40,000 per second: 40,000 x 600 = 24 million messages. If normal traffic then returns to 5,000/s, the consumers have 5,000/s of spare capacity, so draining 24 million takes 4,800 seconds, about 80 minutes. If instead the arrival rate stays above the drain rate forever, the queue grows without bound until it exhausts storage or latency becomes unacceptable. A queue is a shock absorber, not extra capacity. For a sustained increase you must raise the real throughput (more shards, more consumers).

Backpressure is the control signal that closes the loop: use a bounded queue and, when it is full or too old, make producers slow down or fail fast (block, return an error, or return 429) instead of letting memory grow forever.

Load shedding: drop the least important writes

When you can't keep up, deliberately dropping some work is better than letting everything fail. Decide in advance what is expendable:

  • Prioritize by business value: payments and posts matter; likes matter less; view counts and analytics events matter least. Shed from the bottom first.
  • Rate limit per user, per IP or per API key (token bucket or sliding window, often in Redis or at the API gateway), and return 429 Too Many Requests with a Retry-After header. Well-behaved clients retry with exponential backoff and jitter.
  • Sample low-value events: count one in ten views and multiply by ten. The statistics stay accurate for large counts.
  • Shed early and cheaply, at the edge, before the expensive work happens. Dropping a request at the load balancer costs almost nothing; dropping it after it has consumed a database connection costs a lot.
  • Circuit breakers stop sending traffic to a struggling dependency so it can recover.

The trade-off is explicit: you are choosing to lose or reject some data, so it is only acceptable for data that is approximate or recoverable. Say which data you would never drop.

Batching and write coalescing: do less work per write

Each database write has a large fixed overhead (network round trip, parsing, transaction begin and commit, WAL flush, lock acquisition) on top of the tiny payload. Combining many small writes into one amortizes that overhead.

  • Batch inserts: INSERT many rows in one statement or use bulk APIs (COPY, Cassandra batches within one partition, DynamoDB BatchWriteItem), flushing every N items or every few milliseconds, whichever comes first.
  • Coalesce counters: instead of 10,000 statements of UPDATE posts SET likes = likes + 1 on one hot row, keep an in-memory (or Redis INCR) counter and flush likes = likes + 10000 once per second. A million likes per minute against a single post becomes about 60 database updates.
  • Stream aggregation: events flow into Kafka, a stream processor (Flink, Kafka Streams, Spark Streaming) aggregates them in windows, and only the aggregates are written.
  • Group commit: many databases already do this internally, flushing the WAL once for a group of concurrent transactions.

Costs: added latency (a write waits for the batch window), and risk of loss if buffered, unflushed data lives only in the memory of a process that crashes. Mitigate by buffering into a durable log first, keeping windows short, or only batching data you can afford to lose a few seconds of.

Pros of buffering and combining

  • Smooths spikes so you don't provision for the peak
  • Dramatically fewer database operations
  • Decouples the API from database health
  • Removes hot-row contention for counters

Cons

  • Writes become delayed and eventually consistent
  • Duplicates and reordering must be handled
  • In-memory buffers can lose data on a crash
  • More infrastructure to run and monitor

Short answerQueue vs pub/sub, Kafka vs RabbitMQ

The short answer

Scaling writes through a queue is a producer/consumer problem. Each write must be applied once, by one writer, at a steady rate the database can sustain. That is a work queue with competing consumers, partitioned by the shard key.

Add pub/sub on top, not instead, when the same write must also reach other systems (search index, cache invalidation, analytics, notifications). Each of those is a separate subscription with its own lag and failures.

Which broker: for plain "absorb the spike and write asynchronously", a simple work queue is the default: SQS or RabbitMQ. They give you per-message acks, retries, a dead-letter queue and easy consumer scaling, with little to run. Kafka is a distributed log whose natural model is publish/subscribe. It can behave like a queue through consumer groups, but with real limits. Reach for it only when you need very high sustained volume, strict per-key ordering at scale, replay, or several downstream systems reading the same stream.

The full comparison (work queue vs pub/sub, Kafka vs RabbitMQ, how to apply it to a write path, and the pitfalls) is in Long-Running Tasks: Queues, pub/sub and brokers.

Trade-offs & pitfalls

Every technique here trades something away. Be ready to name the cost of each choice.

Sharding adds permanent complexity

You pay for sharding forever: routing logic, schema migrations across N databases, backups, monitoring per shard, and a much harder debugging story. Delay it as long as the numbers allow, and prefer a database that shards for you.

The shard key locks in your access patterns

Queries on the shard key are fast and everything else is scatter-gather or needs a secondary structure. Changing the shard key later means migrating all data. Choose it from the dominant access pattern, and say what you gave up.

Hot partitions

Uneven keys, skewed tenants and celebrities create hot shards that no amount of horizontal scaling fixes. Salting, coalescing, range splitting and isolation are the toolkit; monitor per-shard and per-key traffic to catch it early.

Consistency across shards

Joins, global uniqueness constraints, and multi-row transactions that span shards are costly or unavailable. Keep related data on one shard, or use sagas and idempotent steps (see Multi-Step Processes) and accept eventual consistency where the business allows.

Resharding and rebalancing

Moving data under live traffic is slow and risky. Use consistent hashing or many logical shards, rate-limit the migration so it doesn't starve production traffic, and rehearse it.

Asynchrony and idempotency

Queues, batching and retries mean writes can be delayed, duplicated or reordered. Design consumers to be idempotent, use event IDs for dedupe, and be explicit about what users see while writes are in flight.

Durability versus throughput

Almost every speed-up here (group commit, async replication, in-memory buffers, relaxed fsync) widens a window in which an acknowledged write can still be lost. Match the setting to the data: be strict for money and orders, relaxed for views and telemetry.

When NOT to use it

  • You haven't hit the limits of one node. A tuned, well-provisioned database with sensible indexes handles a surprising amount of write traffic. Sharding "just in case" buys you pain without benefit. Do the math first.
  • The bottleneck is reads. If the system is read-heavy, caching and replicas (see Scaling Reads) are cheaper and simpler than sharding.
  • The workload is dominated by cross-entity transactions or joins. If most operations must atomically touch data that cannot be co-located, sharding makes them slow or impossible. Consider a scale-up first, or a distributed SQL database, or rethink the data model.
  • A single hot item is the real problem. If one key carries the load, more shards won't help. Use coalescing, salting or contention techniques instead.
  • The load is sustained, not bursty. A queue cannot fix a permanent capacity shortfall. It only postpones the failure.
  • Data can't be dropped, delayed or reordered. If every write must be synchronous, immediately visible and strictly ordered across the system (for example a ledger), avoid load shedding and heavy batching and look for strong-consistency designs.

Interview script

Say it like this
"This is write-heavy: about 100K writes per second at peak, which is more than one primary can take. Replicas won't help, because every replica still applies every write. So I'd first confirm one tuned node can't do it, then shard. I'd hash-shard the likes and views by post ID so writes spread evenly, using consistent hashing with virtual nodes so adding a shard only moves a small slice of data, and keep each shard replicated for availability. The trade-off is that 'all posts by a user' becomes scatter-gather, so I'd keep a second table sharded by user ID for that query. For a viral post, the hot key is a problem, so I'd coalesce like counters in memory and flush every second, or salt the counter key. For bursts, I'd put a durable work queue in front, SQS or RabbitMQ by default, keyed by post ID so each post has one writer, rate limit and shed low-priority events like view counts first, and batch the writes into the database. I'd only move to Kafka if I needed replay or other consumers, like search and analytics, reading the same stream. I'd watch consumer lag, because a queue only buys time if the spike never ends."

Deep-dive Q&A

Why don't read replicas help with write scaling?

Replication works by shipping every change from the primary to each replica and having the replica apply it. So each replica performs the same write work as the primary. Adding replicas multiplies read capacity, but the write capacity of the system is still bounded by what one machine can apply. Even in multi-primary setups, each primary must eventually apply every write, and you add conflict resolution on top. To scale writes you have to partition the data so each machine handles only part of it.

How would you choose a shard key for a social app's posts and likes?

Start from the access patterns. Likes and views are huge in volume, are written per post, and are read as per-post counts, so sharding them by post ID spreads writes evenly and makes the per-post lookup single-shard. The cost is that "posts liked by user X" would scatter, so I'd keep a separate table keyed by user for that query. Posts themselves might be sharded by author so profile pages hit one shard, accepting that very active users skew load, which I'd handle by monitoring and isolating whales. I'd avoid country (badly skewed) and timestamp (monotonic, so one shard takes all new writes). The key point is that there is no perfect key; I name the dominant query and optimize for it.

Why consistent hashing instead of hash(key) % N, and what are virtual nodes for?

With modulo, changing N changes the shard of roughly N/(N+1) of all keys (75% going from 3 to 4 shards), forcing a huge data migration or a cache-miss storm. Consistent hashing puts nodes and keys on one ring and assigns each key to the next node clockwise, so adding or removing a node only moves the keys in one arc, roughly K/N keys, and only between that node and its neighbor. Plain consistent hashing with few nodes has uneven arcs, and a dead node dumps everything on one neighbor. Virtual nodes put each physical machine at many (often 100 to 256) positions on the ring, which evens out load, lets bigger machines take more vnodes, and spreads a failed or new node's data across many peers. Remaining caveats: it doesn't fix hot keys, the membership map still has to be distributed (gossip, etcd), and moved data still has to be streamed.

One celebrity's post is getting millions of likes and its shard is melting. What do you do?

Adding shards doesn't help since the key is on one shard. First coalesce: buffer likes in memory or Redis and flush an aggregate count every second or so, which turns millions of writes into a few updates. If the key must take raw writes, salt it into N sub-keys (post:123#0..N-1), write to a random one, and sum on read, accepting a more expensive read for hot keys only. Longer term, detect hot keys by monitoring, give very hot entities their own capacity via a directory, and decide whether like counts need to be exact or can be approximate and eventually consistent.

Queue, load shedding or batching: which do you use for a sudden spike, and what if it doesn't end?

They solve different parts. Batching reduces the cost per write, which raises effective capacity at all times. A queue absorbs a temporary excess and drains it later, but only if average arrival rate is below the drain rate. Load shedding protects the system when even that isn't enough, by dropping the least valuable writes (views before likes before posts) and rejecting excess with 429. If the spike never ends, the queue grows without bound, so you need real capacity: more shards, more consumers (bounded by partition count), and backpressure so producers are throttled. Monitor consumer lag to know which regime you are in.

Should the write queue be a work queue or pub/sub?

A work queue (producer/consumer with competing consumers). Each write must be applied once, by one writer, so a message should go to exactly one consumer. Fan-out would apply it several times to the same database. Use pub/sub for the other things that care about the write (search, cache invalidation, analytics), as separate subscriptions on the same stream so their lag and failures stay independent of the write path. For the full comparison, including Kafka vs RabbitMQ, see Queues, pub/sub and brokers in Long-Running Tasks.

How do you handle transactions and resharding in a sharded system?

Avoid cross-shard transactions by choosing a shard key that co-locates data which must change together, and by denormalizing. When you can't, use two-phase commit (a distributed SQL database does this for you, at a latency cost) or a saga of idempotent steps with compensations. For resharding, avoid modulo placement. Use consistent hashing or many fixed logical shards (for example 1,024 slots over 8 machines) so rebalancing means moving whole slots, backfill the new location while streaming ongoing changes, verify, switch routing, then delete old data, rate-limiting the copy so production traffic isn't starved.
