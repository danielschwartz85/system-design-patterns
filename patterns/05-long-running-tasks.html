Pattern 05 of 08

Long-Running Tasks

Some work simply takes too long to finish inside one HTTP request. Instead of making the user wait, the API records the job, puts it on a queue and replies immediately, while a separate pool of workers does the slow part in the background.

Job queues Worker pools Retries & DLQ Idempotency

TL;DR

If an operation takes more than a few seconds, or is unpredictable in duration, split the request in two: a fast accept step and a slow do the work step, connected by a queue.

  1. The API server validates the request, writes a job record, puts a message on a queue and returns a job ID in milliseconds (HTTP 202 Accepted).
  2. A worker pool pulls jobs off the queue and processes them at its own pace. Workers scale independently of the web tier (small cheap machines for the API, big GPU boxes for transcoding).
  3. The client checks progress by polling GET /jobs/{id} (or gets notified by webhook or push) and fetches the result when the job succeeds.
  4. Make it reliable: queues deliver at-least-once, so handlers must be idempotent; failed jobs retry with exponential backoff and jitter; jobs that keep failing land in a dead-letter queue (DLQ) so one bad input is not retried forever.

The most common mistake is the opposite one: going async for work that takes 200 milliseconds. The synchronous version is far simpler and the user gets the answer immediately. Reach for this pattern only when the work genuinely does not fit in a request.

Recognize it when…
  • The prompt mentions video transcoding, image or document processing, report or PDF generation, bulk exports, or ML inference/training.
  • Something must be sent to millions of people (newsletters, push notifications, email campaigns).
  • The operation calls a slow or flaky third party (payment processor, email provider, web crawler).
  • A step is "after the upload, we then process the file" (see Handling Large Blobs).
  • You hear "this takes minutes," "the request times out," or "users shouldn't have to wait."

The problem

Picture a running app called Stride that builds every user a year-in-review PDF. Rendering one means pulling twelve months of activity, drawing maps and charts, and laying out a document. Say it takes about 90 seconds.

If the API server does that inside the request, three things go wrong:

  • Timeouts cut the connection. Load balancers and gateways have idle or request timeouts (AWS ALB defaults to 60 seconds, API Gateway REST APIs cap at roughly 29 seconds, and many proxies and browsers give up somewhere between 30 and 120 seconds). The caller sees a 504 even though the server keeps working.
  • The work is wasted and the server stays busy. Nobody is listening for the response any more, but the CPU is still burning on it. The user retries, which starts a second copy of the same expensive job.
  • One slow request starves everything else. A server has a limited number of threads, workers or connections. A few hundred 90-second requests can occupy all of them, so cheap requests like "load my profile" start failing too. The web tier now needs the hardware of the most expensive operation.

Other, less visible, problems: you cannot deploy or restart a server without killing in-flight work, you cannot absorb a traffic spike (every request must be served right now or fail), and a flaky downstream dependency turns directly into user-facing errors.

The core idea in one sentence

Decouple accepting work from doing work. The user needs an acknowledgement quickly; they do not need the result quickly, and the system does not need to produce it at the moment of the request.

When it comes up

Any design with a heavy, slow or bursty step. Typical prompts:

  • YouTube / Netflix / Dropbox: transcode an uploaded video into many resolutions, generate thumbnails, scan for malware.
  • Report and export features: "download all my data," CSV exports of millions of rows, analytics reports.
  • Email, SMS and push at scale: newsletters, notification fan-out, digest emails.
  • Web crawler: fetching and parsing pages is slow, rate-limited and failure-prone.
  • Payments and order fulfilment: calling card networks, shipping providers, third-party APIs with their own latency.
  • ML and AI features: inference on large inputs, batch embedding, model training.
  • Any place the prompt says "and then process it." Often the follow-on from file upload.

Sync or async? The decision rule

There is no universal cutoff, but a useful rule of thumb:

Start with the smallest design that removes the work from the request path, then add reliability and scale only as the requirements demand. Each step below builds on the one before it.

Step 1Queue plus worker pool

Put a message queue between the thing that accepts requests and the thing that does the work. The API server does the cheap, bounded part: authenticate, validate, store a job record, enqueue a message and return. A separate fleet of workers (processes that loop forever, pulling a message, doing the work, acknowledging it) does the expensive part. (Choosing between a work queue and pub/sub, and between SQS, RabbitMQ and Kafka, is covered in the deep dive at the end of this section.)

Why this helps

  • Fast, predictable API latency. The request only validates and enqueues, so it returns in milliseconds no matter how heavy the work is.
  • Independent scaling. Web servers are small, cheap and stateless. Workers can be big, memory-rich or GPU-equipped machines, and you can run as many or as few as you want.
  • Burst absorption. The queue is a buffer. A spike of 100,000 jobs piles up in the queue instead of crashing the system, and workers drain it at a steady rate (see Scaling Writes).
  • Failure isolation. If workers die or a downstream service is slow, the API keeps accepting work. Deploys and restarts do not drop jobs, because they live in the queue.
  • Pull-based flow control. Workers take work only when they have capacity, so they are never overwhelmed the way a push-based design could be.

Pros

  • Fast responses and no timeouts
  • Workers scale separately from the web tier
  • Spikes are smoothed out by the queue
  • Work survives deploys and crashes

Cons

  • Result is not immediate; the UX needs a pending state
  • More infrastructure to run and monitor
  • Duplicates and retries become your problem
  • Harder to debug than a single stack trace

Step 2A job record and a status API

A queue message vanishes once consumed, so the system needs a durable job record the user can ask about. When the API accepts a request it inserts a row, then enqueues the job ID. Workers update that row as they go.

jobs
  id            uuid  primary key
  type          text            -- 'year_in_review_pdf'
  status        text            -- queued | running | succeeded | failed | canceled
  params        jsonb           -- inputs, or a pointer to them
  progress      int             -- 0..100, optional
  attempts      int             -- how many times it has been tried
  result_url    text            -- where the output lives (e.g. an object-store key)
  error         text            -- last failure reason
  idempotency_key text unique   -- dedupes client retries of POST
  created_at, started_at, finished_at, updated_at  timestamptz

API shape

Return 202 Accepted (not 200 or 201): the request was understood and queued, but the work is not done. Include the job ID in the body and a Location header pointing at the status resource.

POST /v1/reports
Idempotency-Key: 7f3c9a1e-...
{ "user_id": 42, "year": 2025 }

HTTP/1.1 202 Accepted
Location: /v1/jobs/9b1d...
Retry-After: 5
{ "job_id": "9b1d...", "status": "queued" }

GET /v1/jobs/9b1d...
200 OK
{ "job_id": "9b1d...", "status": "running", "progress": 60 }
{ "job_id": "9b1d...", "status": "succeeded",
  "result_url": "https://cdn.example.com/reports/9b1d.pdf" }
def create_report(req):
    key = req.headers["Idempotency-Key"]
    job = db.insert_or_get(jobs, idempotency_key=key,        # unique index: same key
                           type="year_in_review_pdf",        # returns the same job
                           params=req.json, status="queued")
    if job.is_new:
        queue.send({"job_id": job.id})                       # see "outbox" note below
    return Response(202, {"job_id": job.id, "status": "queued"},
                    headers={"Location": f"/v1/jobs/{job.id}"})
The dual-write gap

"Insert the row, then enqueue" is two separate writes. If the process dies between them you have a job that never runs. Fixes: use the transactional outbox pattern (write the job row and an outbox row in one database transaction, and a relay publishes outbox rows to the queue), or run a periodic sweeper that re-enqueues jobs stuck in queued for too long. Workers must tolerate the occasional duplicate this causes, which is the next step.

Step 3Safe delivery: acks, visibility timeouts and idempotency

The hard part of a job queue is not moving messages around. It is deciding what happens when something goes wrong halfway through. The answer is built from three ideas: an acknowledgement, a visibility timeout and an idempotent handler.

Delivery guarantees

GuaranteeMechanicsFailure modeFits
At-most-onceRemove the message from the queue before (or as) it is processed.Worker crashes mid-job: the job is lost forever.Best-effort, droppable work (metrics, cache warming).
At-least-onceRemove the message only after the work succeeds (ack). If no ack arrives, redeliver.Worker finishes but dies before acking, or is merely slow: the job runs twice.The default for real work. Pair it with idempotency.
"Exactly-once"In practice: at-least-once delivery plus idempotent processing, so duplicates have no extra effect.Any side effect outside your transaction boundary (an email, a charge) can still repeat unless you dedupe it.Payments, billing, anything where a duplicate is harmful.

Be careful with the phrase "exactly-once." Brokers can dedupe sends within a window (SQS FIFO does this for a few minutes) and Kafka offers transactions that give exactly-once semantics within Kafka, but once a worker calls an external system, the network can fail after the call succeeds, and the only defence is making that call safe to repeat. In an interview say: "the queue gives at-least-once; I make the handler idempotent so the effect is exactly-once."

Ack, nack and the visibility timeout

In SQS-style queues a received message is not deleted; it becomes invisible for a configurable visibility timeout (default 30 seconds in SQS, maximum 12 hours). Three outcomes follow:

  • Ack (delete): the worker finished, so it deletes the message. Done.
  • Nack / release: the worker knows it failed (RabbitMQ basic.nack, or set the visibility timeout to 0 in SQS) so the message goes back for another attempt, ideally after a delay.
  • Silence: the worker crashed or hung. When the timeout expires the message becomes visible again and another worker picks it up. This is the self-healing mechanism, and also the source of duplicates.

Set the timeout comfortably above the normal job duration. Too short and healthy slow jobs get redelivered to a second worker while the first is still running. Too long and a crashed worker's job sits idle for ages before anyone retries it.

Heartbeats for long jobs

When job duration is variable, do not guess a huge timeout. Use a short one and have the worker heartbeat: periodically extend the lease while it is still alive (SQS ChangeMessageVisibility, RabbitMQ consumer heartbeats and a delivery timeout, Temporal activity heartbeats, a locked_until column that workers keep bumping). A crashed worker stops heartbeating, so its job is reclaimed within seconds, not hours.

Why duplicates really happen

  • The worker finished but crashed or lost the network before the ack arrived.
  • The visibility timeout expired during a legitimately slow job and the message was redelivered while the first worker was still going.
  • A deploy or autoscaler killed the worker mid-job.
  • The API retried the enqueue after a timeout, or a client double-clicked or retried the POST.
  • The broker itself redelivered after a failover or partition rebalance.

Duplicates are not a bug to eliminate. They are a property to design for.

Making handlers idempotent

An operation is idempotent if doing it twice has the same effect as doing it once. Techniques:

  • Idempotency key on the request. The client sends a unique key with the POST; the API enforces a unique constraint so the same key returns the same job instead of creating a new one.
  • Check state before acting. Look up the job; if it is already succeeded, just ack and move on.
  • Claim with compare-and-set. UPDATE jobs SET status='running', worker=? WHERE id=? AND status='queued' so only one worker wins. Extend this with a lease (locked_until) so a dead worker's claim can be taken over.
  • Deterministic outputs. Write the result to a key derived from the job ID (reports/{job_id}.pdf) so a rerun overwrites the same object instead of creating a second one.
  • Dedupe table for side effects. Record (job_id, step) in a unique-indexed table in the same transaction as the effect, or pass the job ID as an idempotency key to the downstream API (Stripe and most payment APIs support this).
  • Prefer set over increment. "Set status to shipped" is idempotent; "add 1 to the counter" is not.

A worker loop

while not shutting_down:
    msgs = queue.receive(max_messages=1, wait_seconds=20,   # long polling
                         visibility_timeout=120)
    for m in msgs:
        job = db.get_job(m.job_id)
        if job.status in ("succeeded", "canceled"):          # duplicate delivery
            queue.ack(m); continue
        if not db.claim(job.id, lease_seconds=120):          # compare-and-set
            continue                                         # someone else owns it

        try:
            with heartbeat(m, every=60, extend_by=120):      # keep the lease alive
                out_key = f"reports/{job.id}.pdf"            # deterministic output
                render_pdf(job.params, out_key)              # may take minutes
            db.finish(job.id, "succeeded", result_url=url_for(out_key))
            queue.ack(m)                                     # delete only after success
        except RetryableError:
            queue.release(m, delay=backoff(m.receive_count)) # nack with a delay
        except FatalError as e:
            db.finish(job.id, "failed", error=str(e))
            queue.ack(m)                                     # no point retrying

Step 4Retries, backoff and dead-letter queues

Failures are normal at this scale: a dependency times out, a rate limit trips, a spot instance disappears. The system should retry the failures that might succeed next time and quarantine the ones that never will.

Retryable versus non-retryable errors

  • Retry: timeouts, connection resets, HTTP 429 and 5xx, deadlocks, lease or lock conflicts, "dependency temporarily unavailable."
  • Do not retry: validation errors, HTTP 4xx like 400 or 404, a corrupt or unsupported file, permission errors, or a bug that will throw the same exception every time. Retrying these only wastes capacity and delays the real fix.

Exponential backoff with jitter

Do not retry immediately and do not retry on a fixed interval. If a dependency is struggling, hammering it makes things worse, and if thousands of jobs failed at the same moment they will all retry at the same moment too, causing a retry storm.

delay = min(cap, base * 2 ** attempt)     # 1s, 2s, 4s, 8s ... capped at, say, 5 min
delay = random.uniform(0, delay)          # "full jitter": spread retries out

Jitter randomizes the delay so retries spread across time instead of arriving as a wave. Also set a maximum attempt count (commonly 3 to 10), and consider a circuit breaker or retry budget so that when a dependency is clearly down, workers stop hammering it and pause the queue instead.

How you implement the delay depends on the broker: SQS has per-message delay (up to 15 minutes) and visibility timeouts; RabbitMQ commonly uses a TTL'd "wait" queue that dead-letters back to the work queue; BullMQ, Sidekiq and Celery have built-in attempts and backoff settings; Cloud Tasks has configurable retry policies natively.

Poison messages and the dead-letter queue

A poison message is one that can never succeed: a corrupted video, a malformed payload, a job that triggers a crash. Without a limit, it gets redelivered forever, burns worker capacity and can block messages behind it (especially in ordered or partitioned systems). Worse, a poison message that kills the worker outright (an out-of-memory crash) never gets a chance to report its own failure.

The fix is a dead-letter queue (DLQ): after a message has been received more than maxReceiveCount times (SQS calls it exactly that), the broker moves it to a separate queue. Counting deliveries at the broker is important because it works even when the worker crashes before it can say anything.

  • Alert on it. A DLQ nobody watches is a silent data-loss bug. Alarm on queue depth above zero or on the age of the oldest message.
  • Keep context. Store the error, stack trace, attempt count and original payload so someone can diagnose it.
  • Redrive. After fixing the bug, replay DLQ messages back to the main queue (SQS has a built-in redrive feature). Idempotent handlers make this safe.
  • Mind retention. In SQS the retention clock counts from the original enqueue time, so give the DLQ a longer retention period than the source queue.
  • Ordered queues are special. In FIFO queues or Kafka partitions, one stuck message blocks everything behind it. Common practice is to move failed messages to a retry topic or DLQ so the main stream keeps flowing.
  • Update the job row to failed with a user-readable error so the user is not left staring at "running."

Step 5Scaling the workers: pools, priorities, limits and autoscaling

Separate worker pools per job type

Different jobs have different resource profiles and failure modes. Give each its own queue and its own worker fleet:

  • Video transcoding needs GPUs or many CPU cores; sending email needs almost nothing but many concurrent connections; PDF rendering may need lots of memory.
  • A flood of low-value jobs (a million newsletter emails) must not starve a high-value one (a password-reset email). Separate queues give you isolation and let you size and scale each pool independently.
  • Workers can be deployed, versioned and rolled back separately from the API.

Priorities

Most brokers do not have great built-in priority support, so the usual approach is multiple queues (critical, default, bulk) with workers that poll the high-priority queue first, or a weighted share of workers per queue (Sidekiq and Celery both support this). Watch for starvation of the lowest tier and consider aging or a minimum share. RabbitMQ also supports per-queue priority levels natively, with a modest cost.

Concurrency limits and rate limiting

Workers can overwhelm whatever they call. If 500 workers all hit a third-party email API that allows 100 requests per second, you will get throttled and burn retries. Cap parallelism per worker and per job type, use a shared token-bucket rate limiter (for example in Redis), and respect 429 and Retry-After. Per-tenant limits keep one big customer from monopolizing the pool ("noisy neighbour").

Backpressure and autoscaling

The queue gives you a free backpressure signal. Do not scale on worker CPU; scale on the thing that actually measures unmet demand:

  • Queue depth (backlog per worker) and, better, age of the oldest message. Age directly measures how late jobs are running against your SLO.
  • Tools: KEDA on Kubernetes scales deployments from SQS, RabbitMQ, Kafka lag or Redis list length (and can scale to zero). AWS Auto Scaling groups or ECS services can scale on a "backlog per instance" CloudWatch metric. Lambda with an SQS trigger scales automatically up to a configured concurrency.
  • Cap the scale-out to protect downstream databases and APIs; unbounded workers just move the bottleneck.
  • If producers still outrun the maximum capacity, protect the system: bound the queue, reject or shed low-priority work with a 429/503, and tell clients to retry later. An unbounded backlog that is days long is a hidden outage.

Step 6Very long jobs: chunking, checkpoints and graceful shutdown

A single job that runs for an hour is fragile: the longer it runs, the more likely a worker dies, a deploy rolls out or a spot instance is reclaimed, and restarting from zero wastes everything. Two strategies reduce that risk.

Split into chunks: fan-out and fan-in

A coordinator job breaks the work into many small, independent tasks (a video into 10-second segments, an export into 100,000-row pages, a newsletter into batches of 1,000 recipients) and enqueues each one. This is fan-out. Workers process chunks in parallel, so total time shrinks and a failure only costs one small chunk. When all chunks finish, a final step merges them: fan-in (concatenate segments, assemble the file, mark the parent job done). Track completion with a counter (atomic decrement of "chunks remaining") or by querying chunk rows. Each chunk must be idempotent and retried independently.

Checkpointing

If a job cannot be split, save progress periodically (a cursor, an offset, intermediate files in object storage) so a retry resumes where the last attempt stopped instead of restarting. This is the same idea as ML training checkpoints. Combine it with heartbeats so a stalled worker is detected quickly.

Graceful shutdown and spot interruptions

  • Handle SIGTERM: stop pulling new messages, finish or checkpoint the current job, and exit. Kubernetes sends SIGTERM then SIGKILL after terminationGracePeriodSeconds, so set it long enough, or release the message so another worker picks it up right away.
  • Spot and preemptible instances are much cheaper but are reclaimed with short warning (AWS gives a two-minute notice). They are a good fit for workers precisely because jobs are retryable and idempotent. Watch for the notice, checkpoint and release the message.
  • Never ack before the work is durably finished, otherwise a kill during shutdown loses the job.

Step 7Scheduling, delays, and when to graduate to a workflow engine

  • Delayed jobs: "send this reminder in 24 hours" or "retry in 5 minutes." Use per-message delays (SQS up to 15 minutes), delayed queues (BullMQ, Sidekiq's perform_in, RabbitMQ plugin), or a scheduler (Cloud Tasks, EventBridge Scheduler) for longer horizons. For arbitrarily distant times, store them in a table keyed by run_at and have a poller enqueue what is due.
  • Recurring jobs (cron): nightly reports, cleanup. Run the scheduler as a single leader or use a distributed lock, otherwise every instance fires the job and you get N duplicates. Make the job itself idempotent anyway.
  • Workflow engines: a queue is great for a single unit of work. Once the work is many dependent steps over hours or days, with branching, waiting for humans or external events, timers and compensation when a step fails, hand-rolling it on queues turns into a tangle of state machines. Use a durable workflow engine such as Temporal, AWS Step Functions or Airflow. See Multi-Step Processes.

Deep diveQueues, pub/sub and brokers

"Put a queue in front of it" hides two decisions: which messaging model you want (a work queue or publish/subscribe), and which broker implements it (Kafka, RabbitMQ, SQS and so on). They are often confused, so it is worth separating them.

The short answer

Offloading work through a queue is a producer/consumer problem. Each write must be applied once, by one writer, at a steady rate the database can sustain. That is a work queue with competing consumers, partitioned by the shard key.

Add pub/sub on top, not instead, when the same write must also reach other systems (search index, cache invalidation, analytics, notifications). Each of those is a separate subscription with its own lag and failures.

Which broker: for plain "absorb the spike and write asynchronously", a simple work queue is the default: SQS or RabbitMQ. They give you per-message acks, retries, a dead-letter queue and easy consumer scaling, with little to run. Kafka is a distributed log whose natural model is publish/subscribe. It can behave like a queue through consumer groups, but with real limits. Reach for it only when you need very high sustained volume, strict per-key ordering at scale, replay, or several downstream systems reading the same stream.

Two messaging models

  • Producer/consumer (point-to-point, "work queue", competing consumers). Producers put messages on a queue. Several consumers read from the same queue, and each message goes to exactly one of them. Once it is acknowledged, it is gone. Its purpose is to distribute work and level load, and you scale it by adding consumers.
  • Publish/subscribe (pub/sub, "fan-out"). Publishers send messages to a topic without knowing who is listening. Every subscription receives its own copy of every message. Its purpose is to decouple a producer from many independent interested parties. Adding a subscriber adds another reader of the same data, not more throughput for anyone else.

The two are not mutually exclusive

Real systems combine them: fan out first, then give every subscriber its own queue, where that subscriber's workers compete for messages.

  • SNS + SQS: publish once to an SNS topic, and each subscribing service has its own SQS queue with its own workers.
  • RabbitMQ: a fanout or topic exchange copies each message into every bound queue. Each queue can have several competing consumers.
  • Google Pub/Sub: a topic has several subscriptions. Each subscription is, in effect, a queue shared by that subscriber's workers.
  • Kafka: one topic read by several consumer groups. Within a group, each partition goes to one consumer (queue semantics). Across groups, every group sees every message (pub/sub semantics).

Applying it to a write path

A common use of a queue outside of job processing is buffering database writes (see Scaling Writes). Work through what that write path needs:

  1. Each write must be applied exactly once to the database. That points to a work queue with competing consumers. In a pure pub/sub fan-out where three subscribers all write the same row to the same database, you would write it three times, which is an anti-pattern.
  2. You are protecting the database's throughput. The consumers' job is to drain at a steady rate the database can sustain. More consumers means a faster drain, up to what the database allows.
  3. Align partitions with shards. Key the queue by the same key you shard on. Messages for one key go to one partition and so to one consumer. That preserves per-key order, avoids two writers fighting over the same row (see Contention), and lets each consumer batch writes for its own shard. The key-to-partition mapping works like the key-to-shard mapping described under consistent hashing. You do not need Kafka for this: SQS FIFO queues give per-key ordering through message group IDs, and with RabbitMQ you can run one queue per shard (or use a consistent-hash exchange) with one consumer each.
  4. Apply pub/sub for everything else that cares about the write. Search indexing, cache invalidation, analytics and notifications are separate consumer groups or subscriptions on the same stream. Each has its own lag and can fail or be replayed independently, without touching the write path.
  5. Make the consumers idempotent and acknowledge late. Delivery is at-least-once, so use upserts or event IDs to dedupe. Commit the offset or send the ack only after the database write succeeds. Acknowledging first loses a write if the consumer crashes in between.

Kafka vs RabbitMQ

Both can run the write path, but they are built on different ideas.

  • Kafka is a distributed commit log. A topic is split into partitions. Each partition is an ordered, append-only log replicated across brokers (one leader, several followers). Consumers pull and track their own position, called an offset. Messages are retained for a configured time or size (or compacted to keep the latest value per key) whether or not anyone has consumed them. Ordering is guaranteed within a partition only. In a consumer group each partition is read by at most one consumer, so parallelism is capped by the partition count. Producers choose the partition, usually by hashing a key.
  • RabbitMQ is a smart broker. Producers publish to an exchange (types: direct, topic, fanout, headers). Bindings route the message to one or more queues. The broker pushes messages to consumers, limited by a prefetch count, and tracks each message's acknowledgement. An acknowledged message is deleted. A negative-acknowledged one is requeued or dead-lettered. It has per-message and per-queue TTLs, priority queues, dead-letter exchanges and flexible routing built in. Quorum queues (Raft-replicated) are the durable choice, and a separate streams feature offers a Kafka-like replayable log.

Choosing for a write path. Start from the job: you want a durable buffer that smooths a spike, with a retry and a dead-letter queue, so the database is written at a steady rate. That is exactly what SQS or RabbitMQ are built for, they are simple to operate, and they are the right default. SQS is the zero-ops choice on AWS; RabbitMQ is the choice when you also want rich routing, priorities or low latency and can run a broker.

Move to Kafka only when you can name the reason:

  • Sustained very high volume (say 100K or more writes per second), where a log's sequential I/O and batching matter.
  • Strict per-key ordering at that scale, via partitions.
  • Replay: you need to re-read history to rebuild a consumer, fix a bug, or backfill a new system.
  • Many independent consumers of the same stream (the pub/sub side of Kafka), such as search, analytics and a data lake.

If none of those apply, Kafka adds partition planning, rebalances, and retry topics you must build yourself, for no benefit. Other managed options include Kinesis, Google Pub/Sub, and Apache Pulsar (which supports both queue-style and pub/sub-style subscriptions). Redpanda speaks the Kafka protocol with a different implementation.

Pitfalls specific to this choice

  • Plan the partition count up front. It caps consumer parallelism. Adding partitions later changes the key-to-partition mapping (with default hash-modulo placement), which can break per-key ordering during the change. Over-provision moderately instead of starting at one.
  • Hot keys make hot partitions. One viral key sends all its traffic to one partition and one consumer. Salt the key or coalesce before enqueueing (see Hot shards and hot keys in Scaling Writes).
  • Watch consumer lag. It is your headroom signal. Alert on lag growth and on the age of the oldest message.
  • Rebalances pause consumption. When consumers join or leave a Kafka group, partitions are reassigned and processing briefly stalls. Avoid flapping consumers.
  • At-least-once means duplicates. Make writes idempotent, and commit or ack after the database write, never before.
  • A poison message blocks its partition. In an ordered log, one message that always fails stops everything behind it. Send it to a dead-letter or retry topic after a few attempts.
  • Retention is a cost and a promise. Longer retention allows deeper replay but costs disk. Size it for how far back you may need to rebuild a consumer.
If asked: queue or pub/sub, Kafka or RabbitMQ?
"For the write path itself I want a work queue with competing consumers, because each write must be applied once at a rate the database can take. My default is a simple managed queue like SQS, or RabbitMQ, since they give me acks, retries and a dead-letter queue with little to run. I'd key it by the shard key so each key has one writer and order is kept. I'd only move to Kafka if I needed very high sustained throughput, replay, or several other systems, like search and analytics, reading the same events as separate consumer groups."

Trade-offs & pitfalls

Async processing buys you resilience and scale at the price of complexity. These are the failure modes interviewers probe.

Complexity and the end of "just return the result"

You now have a queue, a worker fleet, a job table, a status API and a UX for pending, failed and retried states. Every one of those can break and needs monitoring. This is the main reason not to use the pattern for fast work.

Duplicate execution

At-least-once delivery means a job can run more than once. If the handler sends an email or charges a card without idempotency, users get two emails or two charges. Use idempotency keys, deterministic outputs, state checks and dedupe tables as described in Step 3.

Lost jobs

Jobs vanish through the dual-write gap (row saved, message never sent), through acking before the work is complete, or through queues that are not durable (memory-only Redis lists without persistence, or auto-ack consumers). Use an outbox or a sweeper, ack after success and choose durable queues.

Retry storms and amplification

If every layer retries (client, API, worker, SDK), a brief outage multiplies into a flood. Use exponential backoff with jitter, retry limits, a retry budget or circuit breaker, and retry at one layer rather than all of them.

Poison messages and head-of-line blocking

Without a max receive count and a DLQ, a single bad message loops forever. In ordered queues it also blocks everything behind it. Use DLQs, and for ordered streams, a retry topic.

Ordering and exactly-once expectations

Standard queues (SQS Standard, RabbitMQ with multiple consumers) do not guarantee order, and retries reorder messages further. If order matters per entity (all events for one order), partition or group by key (SQS FIFO message group ID, Kafka partition key) and accept lower parallelism. Often it is better to design the handler to be order-tolerant, for example by comparing version numbers.

Backlog and latency growth

When arrivals exceed capacity, the queue grows without bound and every job gets later and later. Monitor queue age, autoscale, and shed or reject work at the edge before the backlog becomes unrecoverable. Note that a deep queue also means a retried job waits behind the whole backlog.

Visibility timeout mistakes

Too short causes duplicate concurrent execution; too long delays recovery. Use heartbeats to keep a short timeout that still survives long jobs.

User experience

Users need feedback: a visible "processing" state, progress, a clear failure message and a way to retry or cancel. Decide what the UI shows between submit and done, and what happens if the user navigates away (notify by email or push).

When NOT to use it

The most common mistake: going async too early

Many candidates reach for queues, workers and status endpoints the moment a diagram has a "processing" box. If the work takes around 200 milliseconds, just do it inside the request. The synchronous version has no job table, no polling, no retry logic, no duplicate handling and no failure states to explain, and the user gets the result immediately.

  • Fast work. Anything that reliably finishes in well under a second or two. Resizing a small avatar, validating input, computing a recommendation from cached data: do it inline. Adding a queue makes the user experience worse because they now wait for a poll.
  • The user needs the answer to proceed. Login checks, price calculations at checkout, "is this username taken." Async only adds latency and a pending state.
  • You cannot make the work idempotent. If a duplicate would be harmful and you have no way to dedupe, fix that first or keep it synchronous with a transaction.
  • Low and steady volume. If you do a handful of jobs a day, a scheduled script or a thread in the web process might be enough.
  • The slowness is a symptom. If an endpoint is slow because of a missing index or an N+1 query, fix that rather than hiding it behind a queue (see Scaling Reads).
  • The work is a long chain of dependent steps. Reach for a workflow engine, not a pile of queues. See Multi-Step Processes.

A good habit: state your estimate out loud, "this takes about 200 ms, so I'll do it inline; if it grew to minutes I'd move it to a queue." That shows judgement, not just vocabulary.

Deep-dive Q&A

How do you guarantee a job runs exactly once?

You do not, at the queue level. Queues give at-least-once delivery because the only way to avoid losing a job is to redeliver when you are unsure it finished. What you can achieve is effectively-once: make the handler idempotent so duplicates have no extra effect. Concretely, dedupe with an idempotency key and a unique constraint, check job status before acting, write outputs to deterministic keys, claim jobs with compare-and-set, and pass the job ID as an idempotency key to external APIs such as payment providers.

A worker crashes in the middle of a job. What happens?

The message was received but never acked, so after the visibility timeout expires it becomes visible again and another worker picks it up. The job row may still say running, so workers should claim with a lease (locked_until) and be allowed to take over an expired one. For long jobs the worker heartbeats to extend its lease, so a crash is detected within one heartbeat interval instead of waiting for a huge timeout. If the job supports checkpoints, the next worker resumes from the last one. After maxReceiveCount failed deliveries the message goes to the DLQ.

One corrupted file keeps failing. How do you stop it from blocking everything?

Cap the attempts and use a dead-letter queue. Classify errors: a corrupt file is non-retryable, so mark the job failed immediately and ack; unknown or crash-causing failures are caught by the broker's receive count and moved to the DLQ after a few tries. Retries use exponential backoff with jitter so a bad message does not spin hot. Alert on DLQ depth, keep the error context, fix the underlying bug and redrive. In an ordered or partitioned system, move the failing message aside to a retry topic so the rest of the partition keeps flowing.

Should the client poll, or should we use webhooks or WebSockets?

Start with polling a GET /jobs/{id} endpoint: it is simple, stateless and robust, and a modest interval with backoff and a Retry-After hint keeps load low. Add push (WebSocket, SSE, mobile push) when users are watching and expect instant feedback, see Real-Time Updates. Use webhooks for server-to-server consumers, with signed payloads and retries on the sender side. Keep the status endpoint as the source of truth in every case, because notifications can be missed.

How do you scale the workers, and what do you scale on?

Scale on unmet demand, not CPU: queue depth per worker, or better the age of the oldest message against your latency target. KEDA on Kubernetes or an Auto Scaling group driven by a backlog-per-instance metric handle this, and they can scale to zero when idle. Keep a separate pool per job type so GPU, memory-heavy and lightweight jobs are sized independently, cap the maximum so downstream databases and APIs are not overwhelmed, and rate-limit calls to third parties. If demand still exceeds the cap, bound the queue and shed or reject low-priority work instead of letting the backlog grow indefinitely.

Why not just use Kafka for this?

Short version below; the full Kafka vs RabbitMQ comparison is in Queues, pub/sub and brokers.

Kafka is a log, not a task queue. Messages are not removed on consumption; consumers track offsets, and within a consumer group each partition is read by only one consumer, so parallelism is capped by partition count and one slow or poison message blocks everything behind it in that partition. There is no per-message ack, delay or built-in DLQ, so you build retry topics yourself. Kafka shines when you need very high throughput, ordering per key, or replay of history by many independent consumers. For classic "do this task once, retry on failure" work, SQS, RabbitMQ or a Redis-based job library is usually a better fit. In an interview, saying Kafka is acceptable if you explain how you handle retries, ordering and parallelism.

Kafka or RabbitMQ for offloading work or writes?

For simply offloading writes asynchronously, a work queue is the better default: RabbitMQ, or SQS on AWS. You get per-message acks, retries with dead-letter queues, routing, priorities and delays out of the box, and simple operations. Kafka is a retained log whose natural model is pub/sub. It earns its complexity when you have very high sustained throughput, ordering per key at scale (partition by shard key), a need to replay history, or several downstream consumers on the same stream, and it costs you retries, delays and priorities that you build yourself, plus careful partition planning. State the write rate, the ordering requirement and whether anything else needs the stream, then pick.

How can Kafka behave as both a queue and as pub/sub?

Through consumer groups. Within one group, each partition is assigned to a single consumer, so the group's consumers share the work: queue semantics. Different groups each track their own offsets and each receives every message: pub/sub semantics. So the database writers form one group, and a search indexer and an analytics job each form their own group on the same topic. Note that Kafka's native strength is the second behaviour, pub/sub over a retained log. Its queue behaviour is real but constrained: parallelism is capped by partition count, there is no per-message ack or retry, and one poison message blocks its partition. That is why a plain work queue is usually the simpler choice when all you need is async offload.
